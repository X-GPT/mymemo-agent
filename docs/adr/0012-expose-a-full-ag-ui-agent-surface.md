# Expose a full AG-UI agent surface

Run-control vocabulary and terminal behavior are amended by
[ADR-0013](./0013-interrupt-runs-without-ending-conversation-continuity.md).
The retained per-Run Redis Stream transport — entry-id cursors,
`Last-Event-ID` resumption, `activeRun.lastEventId`, the 30-minute
post-terminal retention, the `ResumableStreamStore` adapter, and its Lua/cap/
TTL machinery — is superseded by
[ADR-0014](./0014-producer-buffered-live-stream-over-pubsub.md); every
non-transport decision here remains in force.

Issue #560 stages a replacement AI SDK Agent-query path. Issues #562–#564 add
its canonical Conversation message store, synchronous Runtime invocation,
Postgres-backed Agent session, and reusable Workspace tools. The shared Chat
API may mount the staged route, but production leaves its Runtime unconfigured
and still uses the Run and Run-event authority described below. The production
authority changes must explicitly supersede this decision at hard swap.

MyMemo exposes a plug-compatible AG-UI data plane rather than only borrowing AG-UI-shaped event names. A Run endpoint accepts the standard `RunAgentInput` body and returns a standard AG-UI `BaseEvent` stream; active-Run reconnect emits the same event vocabulary from a per-Run Redis Stream. MyMemo also supplies the persistence, replay, interruption, and history endpoints that AG-UI leaves to the server implementation. The surface advertises resumability only after its sequence and replay contract is implemented and verified.

AG-UI is the interoperable Run data plane, not the owner of MyMemo's Conversation resources. Conversation creation, listing, title search, rename, Archive, Permanent deletion, frozen Scope, ownership, history paging, and artifacts remain MyMemo APIs because AG-UI does not define their lifecycle. `mymemo-web` translates those resources into assistant-ui's Thread-list and history adapters, while assistant-ui remains a replaceable UI dependency.

A new assistant-ui Thread remains a client-only draft until its first send. `mymemo-web` first creates the server Conversation, atomically replaces the selected draft id with the returned Conversation id, and then submits the first Run through the same endpoint as every later Run; if submission fails after creation, the server id remains selected for an idempotent retry. The persisted Conversation title is initialized from the first successfully admitted User message when still unset and changes afterward only through explicit rename. Conversation activity, and therefore list recency, advances on successfully admitted User messages rather than rename, Archive, or Run completion.

`mymemo-web` owns the opaque Conversation-list cursor and implements its own Load-more control before supplying accumulated `regular` and `archived` arrays to assistant-ui. Title search is server-side within the selected archive partition, so search is not limited to already-loaded pages.

The canonical Run endpoint is `POST /v1/conversations/:conversationId/runs`, mirrored by the stateless BFF at `POST /agent/conversations/:conversationId/runs`. The configurable AG-UI `HttpAgent` posts its standard body to that resource URL. `RunAgentInput.threadId` must equal the path Conversation id; a mismatch returns `400` before admission.

Once that endpoint commits Postgres admission, response-transport failure never rolls the Run back. If chat-api cannot read Redis before opening SSE, it returns `503` while retaining the admitted Run; the client retries the identical `RunAgentInput` with the same `runId` and attaches idempotently. If Redis reading fails after SSE opens, chat-api terminates the incomplete connection and the client follows the normal Reconnecting or Recovering path. Neither case interrupts or duplicates the Run.

The stateless Agent BFF mirrors each `/v1/conversations*` resource under `/agent/conversations*`, injects trusted identity, and otherwise preserves chat-api's success status, error status, JSON body, SSE body, and `Last-Event-ID` unchanged. It stores no Run cursor and performs no domain translation. The existing Conversation-create `business_ok` envelope is removed so the whole surface has one transparent relay contract.

The Statsig exposure gate governs only new-work operations: Conversation creation and Run admission. Ownership-checked listing, history, lifecycle mutation, interruption, reconnect, and artifact access bypass exposure so a user can still recover, control, or remove existing data after losing new-work eligibility.

There is no compatibility migration window because the existing custom agent wire has no users. The worker event vocabulary, chat-api AG-UI routes, BFF relay, and `mymemo-web` client switch as one release scope. Issue #344 removes the legacy `POST .../events` user-message/interrupt contract, custom client frames, cursorless Redis Pub/Sub preview, and its two-source projector, leaving the retained per-Run Stream as the sole current live transport. ADR-0014's producer-buffered Pub/Sub replacement is sequenced afterward, so three transports never coexist.

MyMemo defines a restrictive AG-UI input profile at its trust boundary. The authenticated Conversation is authoritative for `threadId`, stored Conversation history is authoritative over repeated client history, and server configuration remains authoritative for Scope, tools, model selection, execution limits, and system context. Non-empty client-supplied `tools`, `state`, `context`, and `forwardedProps` are rejected unless a later capability explicitly admits them.

The client-generated `RunAgentInput.runId` becomes the canonical MyMemo Run id and idempotency key on first admission, and `RUN_STARTED` echoes that same id. Retrying the same id with the same admitted input reattaches to or replays the existing Run rather than creating work. Reusing it with different admitted input returns `409`; lookup under a different Conversation or owner remains indistinguishable from absence with `404`.

The initial input profile is append-only. `messages` must end in one plain-text AG-UI User message, whose client-supplied id and original text become the submitted message recorded for the Run. Earlier messages are neither trusted nor compared with stored history and do not enter execution context; the server reconstructs prior context from its own durable Conversation state. Empty or default `tools`, `state`, `context`, and `forwardedProps` are accepted because the standard body carries those fields, while non-empty values are rejected. `parentRunId`, multimodal input, resume, branching, editing, and regeneration are rejected until a later advertised capability admits them.

Archive is a nullable server timestamp and an explicit reversible no-new-work state, not merely a client list filter. An archived Conversation remains available for history, artifacts, interruption, reconnect, rename, unarchive, and Permanent deletion, but Run admission returns `409` until explicit unarchive. Archive itself returns `409` while a Run is active and never implies interruption; rename remains available while active or archived. Strict `PATCH /v1/conversations/:conversationId` accepts `title` and/or `archived`, and a combined rename-plus-Archive still enforces the active-Run guard.

`DELETE /v1/conversations/:conversationId` performs Permanent deletion only when no Run is active; otherwise it returns `409` and never implicitly interrupts work. One transaction removes the Conversation, permanent history, and Downloadable-artifact metadata, after which reads return `404`; sandbox, Agent-session, and private-object cleanup remains asynchronous and retryable. A missing or foreign Conversation returns `404`, although `mymemo-web` may treat that response from a stale or retried delete as already absent locally.

Run admission, Archive, unarchive, and Permanent deletion lock the same owned Conversation row before checking state or mutating it. `runs.(user_id, conversation_id)` also references `conversations` with `ON DELETE CASCADE`. These database invariants prevent admission after Archive or deletion and prevent deletion from racing active work.

The worker retains ownership of queue supervision, lease fencing, E2B provisioning and renewal, Postgres Claude-session continuity, trusted Tool binding, bounded Tool projection, safe errors, and artifact publication. The `@ag-ui/claude-agent-sdk` adapter is not used as the worker lifecycle owner because its in-memory session map, automatic client-Tool MCP bridge, forwarded option overrides, and direct `query()` ownership conflict with those guarantees. MyMemo may use AG-UI core types and encoding while projecting its already-supervised Claude SDK stream.

Runs and Run events are retained for the Conversation's lifetime and are the authority for its permanent user-visible history; irreversible Conversation deletion removes them. No duplicate message store is introduced, and any future age-based Run cleanup must first establish and migrate to a replacement history authority.

`GET /v1/conversations/:conversationId/history` pages that projection on complete Runs, selecting the newest Runs first and traversing toward older Runs behind an opaque cursor. Within each response page, `runs` is presented chronologically from oldest to newest; `mymemo-web` prepends older pages before already-loaded pages and can flatten messages directly. The response envelope is `{conversation, runs, nextCursor, activeRun}`. Each `runs[]` entry is `{runId, messages, terminalEvent}`: `messages` is an ordered array of standard AG-UI `Message` objects, and `terminalEvent` is the Run's `RUN_FINISHED`, `RUN_ERROR`, or custom `RUN_INTERRUPTED` event, or `null` while active. `nextCursor` and `activeRun` are always present and nullable; `activeRun` retains `{runId, status, lastEventId}` for authorized attachment to the live event stream. The page `limit` counts complete Runs, and no terminal Run is split across pages.

The history envelope's `conversation` carries the owned Conversation's persisted title, frozen Scope, creation/activity timestamps, and archive timestamp, so a deep link needs no separate Conversation-detail request. Unknown internal Run-event types are skipped fail-closed. A malformed payload for a known public projection fails the request with a generic `500` and is logged as corruption rather than presenting incomplete history as authoritative.

On a full refresh during an active Run, history includes that Run as an extra newest entry containing only its submitted User message and `terminalEvent: null`; it does not count against the completed-Run limit. `activeRun.lastEventId` is `"0"`, and reconnect reads the Run's Redis Stream from the beginning, replaying `RUN_STARTED` plus every event currently retained for that Run. If the Run is still queued or has only just been claimed and the worker has not created the Stream yet, chat-api waits for Stream creation rather than treating it as missing. The active Run's Assistant messages are deliberately reconstructed by the event parser rather than imported half-open through `fromAgUiMessages`. A transient reconnect that does not reload history instead resumes after the browser's actual last Redis Stream-backed SSE cursor.

`mymemo-web` uses `@assistant-ui/react-ag-ui`'s [resume-stream integration](https://github.com/assistant-ui/assistant-ui/pull/4224) rather than forking or manually driving its Thread runtime. When history contains an active Run, `ThreadHistoryAdapter.load()` returns `unstable_resume: true` and the adapter always supplies `history.resume()`, closed over that `activeRun.runId`. Omitting `history.resume()` in this state is forbidden because the upstream fallback invokes a fresh `agent.runAgent(...)`, which could submit different work instead of reattaching. The resume generator consumes MyMemo's authorized GET stream and yields `ChatModelRunResult` updates into the existing Assistant message without creating a new `runId` or replaying the Run endpoint.

The MyMemo resume generator still owns transport policy: it captures each transport-level SSE `id`, reconnects the authorized GET stream with `Last-Event-ID`, starts from cursor zero after full history hydration, converts the standard AG-UI events into `ChatModelRunResult` updates, and enters Reconnecting or Recovering under the rules below. Each SSE id encodes the corresponding Redis Stream entry id, remains transport metadata, and is never inserted into an AG-UI event. The last cursor lives only in the active connection's memory: `mymemo-web` does not persist it in `sessionStorage`, because a full refresh obtains the canonical active `runId` from history and deliberately rebuilds that Run from cursor zero. New Runs can still POST through the standard `HttpAgent`; assistant-ui stop control is wired to durable MyMemo Run interruption and retains already-streamed content while that request completes.

While an SSE response is waiting for Stream creation or following a quiet Run, chat-api retains its existing five-second comment ping. The ping is HTTP transport activity only: it has no SSE `id`, is not an AG-UI event, and is never stored or replayed. A ping write failure ends that connection and invokes the same Reconnecting behavior as any other network interruption.

`GET /v1/conversations/:conversationId/runs/:runId/events` authorizes the owned Run and reads its retained Redis Stream after `Last-Event-ID`. It follows an active Run or closes after the terminal event. A missing Stream for an active Run with no `live_stream_failed_at` is a not-yet-started Stream, so the endpoint waits until the worker creates it, the marker appears, or the Run terminalizes. The Stream is never trimmed or expired while the Run is active and remains available for 30 minutes after terminal publication; after that grace period, permanent history is rehydrated from Postgres instead of replaying the expired transport stream. Before opening SSE, the endpoint returns `503` for a temporary Redis read failure only while the Run remains active, so the client stays Reconnecting. It returns `410 {error: "Live stream unavailable", recovery: "history"}` when `live_stream_failed_at` is set, the Stream has expired, the Run terminalized without ever creating one, or a terminal Run's Stream cannot currently be read; in every terminal case Postgres history is already complete. It returns `400` for an invalid cursor and `404` for a missing or foreign Run. The BFF preserves these statuses and forwards `Last-Event-ID` unchanged.

Postgres is the sole Stream-authorization authority. chat-api validates the trusted identity and verifies the owned `{userId, conversationId, runId}` before any Redis read; the opaque `runId` is never treated as a credential, and missing or foreign Runs remain indistinguishable through `404`. MyMemo does not duplicate that binding in a Redis owner key, whose independent TTL and lifecycle could drift into false denials or inconsistent authorization state.

Interruption uses `POST /v1/conversations/:conversationId/runs/:runId/interrupt`, mirrored at `/agent/conversations/:conversationId/runs/:runId/interrupt`; it is not encoded as a client message and does not delete the Run. A queued Run terminalizes as `interrupted`, while a running Run becomes `interrupt_requested`; both return `202 {runId, status}`. Retrying either state, including terminal `interrupted`, returns the corresponding idempotent `202`. A Run already terminalized as `done` or `error` returns `409`; a missing or foreign Run returns `404`. Issue #344 removes the legacy `{type: "user.interrupt", runId}` envelope; before removal it delegated to this same operation.

The worker is the sole Live Stream producer. A Run that terminalizes outside that producer does not cause chat-api or cleanup to synthesize Redis events: queued interruption commits its Outcome to Postgres before any Stream exists, while Reclamation commits `interrupted` for an accepted `interrupt_requested` Run and `error` for other work abandoned by a lapsed Claim. Waiting clients enter Recovering and hydrate the permanent Outcome from Conversation history.

A submitted message is an AG-UI User message. One model response envelope is an AG-UI Assistant message, including a textless Assistant message when it owns Tool calls. Each client-visible Tool invocation receives a stable, opaque, MyMemo-generated UUID exposed as `toolCallId`; the worker maps the provider's Tool-use id to it only for internal correlation. Tool invocations are represented by their owning Assistant message's `toolCalls`, and results are AG-UI Tool messages referring to the same id. Invocations and visible text from one model envelope share its stable MyMemo-generated `messageId`; a Tool-only envelope exposes that identity through its invocations. A Run Outcome is never fabricated as a chat message: it is represented by `terminalEvent`. No separate History-item coordinate id is needed because AG-UI message and Tool identities plus the enclosing Run provide merge and replay identity. These identity rules supersede ADR-0009's uncorrelated Tool projections and ADR-0008's internal-only identity for textless Assistant messages.

Each newly written Tool invocation uses explicit durable lifecycle events: `tool_call_started {toolCallId, toolCallName, parentMessageId}`, one bounded `tool_call_args {toolCallId, delta}`, and `tool_call_completed {toolCallId}`, followed later by `tool_call_result {messageId, toolCallId, content}` when a result exists. They project one-to-one to `TOOL_CALL_START`, `TOOL_CALL_ARGS`, `TOOL_CALL_END`, and `TOOL_CALL_RESULT`. Each lifecycle event is appended to the Redis Stream only after its Postgres commit, so Tool activity remains permanent while the active client consumes one ordered live transport. MyMemo does not rely on implicit `TOOL_CALL_CHUNK` finalization.

AG-UI `ToolMessage` history can mark an error, but the current assistant-ui AG-UI parser does not read an error flag from live `TOOL_CALL_RESULT`. A recoverable Tool error therefore emits the standard result with its fixed client-safe error text, immediately followed by `CUSTOM {name: "mymemo.tool_result_error", value: {messageId, toolCallId}}`. The MyMemo Tool renderer uses that namespaced metadata to render the live failure; generic AG-UI clients may ignore it and still see the safe result text. History uses the standard `ToolMessage.error` field.

If a Run fails or is interrupted with an open Assistant response, its incomplete text remains provisional in the Redis Stream and is not copied into permanent history. A connected client may retain that partial text while an interruption request is pending, but discards it when the request succeeds, `RUN_INTERRUPTED` arrives, or terminal history is recovered. A later history hydration contains only complete Assistant messages and durable Tool activity. `mymemo-web` still overrides the converter's default `requires-action` inference for any unresolved server Tool invocation in a terminal Run.

Run events written before stable Tool correlation exists are not assigned fabricated `toolCallId` values. Such legacy safe projections may be exposed as namespaced AG-UI `CUSTOM` events during event replay, but cannot be represented as standard correlated Tool messages. Newly written Runs must be fully representable in the standard AG-UI message and event model.

The AG-UI message history is a read projection, not the execution transcript and not a second source of truth. Durable MyMemo Run events remain authoritative for permanent history, while a per-Run Redis Stream is authoritative only for live delivery and temporary active-Run replay. Token-level streaming is a required part of the initial surface, not a later enhancement. Each provider response appends `TEXT_MESSAGE_START` and coalesced `TEXT_MESSAGE_CONTENT` events directly to that Redis Stream. When the provider response completes, the worker first appends one `assistant_message_completed {messageId, text}` Run event to Postgres and only then appends `TEXT_MESSAGE_END` to Redis. A textless Tool-owning response still persists a complete Assistant identity and its Tool calls. A failed or interrupted open response has no fabricated completion and its partial text never enters Postgres history.

The Redis Stream also carries the standard AG-UI projections of durable Tool and terminal events, but only after their corresponding Postgres commits. Consequently, the original connection and active-Run reconnect both consume one ordered Redis source; chat-api no longer merges Pub/Sub text with Postgres projection and does not compare provisional text with a later commit. A transient reconnect uses `XREAD` after the last Stream-backed SSE id, while a full refresh reads from the beginning. There is no separate `deltaIndex`. Publishing `TEXT_MESSAGE_END`, a Tool result, or a terminal event before its Postgres commit is forbidden because a client could otherwise observe completed state that permanent history does not contain.

MyMemo uses the low-level `ResumableStreamStore` contract from `assistant-stream/resumable` as the shared split-runtime byte log: after claiming a Run, agent-worker acquires its Stream, appends encoded standard AG-UI event payloads, and finalizes it, while chat-api reads it. A small MyMemo Redis adapter supplies the required active-retention, terminal-TTL, and failure-marker behavior. The high-level `ctx.run()` and `AssistantChatTransport` are not used because they assume the originating HTTP handler owns the producer and target the AI SDK runtime; `mymemo-web` stays on the AG-UI runtime and supplies its MyMemo transport through `ThreadHistoryAdapter.resume()`.

`REDIS_URL` is required configuration in both chat-api and agent-worker and must be an authenticated `rediss://` URL; missing, malformed, or insecure configuration fails startup because the deployed surface promises streaming. Runtime connection or command failure does not fail process health or Run execution: it follows the Stream-failure contract and is reported as operational degradation, avoiding restart loops during a shared Redis outage.

The Redis adapter uses `{deployment}:mymemo:agui:{runId}:stream` and `{deployment}:mymemo:agui:{runId}:meta`. The deployment prefix isolates environments, and the `{runId}` hash tag places both keys in one Redis Cluster slot for atomic operations. Keys contain neither user identity nor message content; Postgres remains the mapping from the opaque Run id to its owner and Conversation.

The adapter implements multi-key mutations with small Redis Lua scripts. Append atomically verifies streaming state and both size caps, performs `XADD`, updates byte and entry counters, and refreshes both TTLs; finalize atomically records the final transport status and synchronizes both TTLs; heartbeat refresh extends both TTLs only while the Stream is still streaming. Acquisition uses `SET ... NX`. A pipeline without these atomic checks is insufficient because process death could otherwise leave the byte log and metadata disagreeing.

The worker may publish only when `acquire(runId)` returns `"producer"`. A `"consumer"` result means an unexpected Stream already exists; the worker does not adopt or append to it, sets `live_stream_failed_at`, and continues the Run without live delivery. Under the claim-once protocol there is exactly one legitimate producer, so accepting an existing Stream could mix the Run with entries from an unknown or stale writer.

Each store entry contains exactly one complete UTF-8 serialized AG-UI `BaseEvent`, without SSE framing. Text is coalesced before append and no serialized event is split across entries. The store assigns the entry's opaque cursor; chat-api reads the payload, emits that cursor as the SSE `id`, and applies SSE encoding at the HTTP boundary. Thus every AG-UI event has exactly one replay cursor while Redis remains independent of HTTP syntax.

One serialized store entry is capped at 32 KiB. `TEXT_MESSAGE_CONTENT` coalescing targets at most 16 KiB for the complete encoded event and splits only on Unicode boundaries; the existing 16 KiB Tool-projection payload cap leaves room for its AG-UI envelope within the store limit. An oversized non-text event is not split or truncated again at the transport layer: it fails the Live Stream, sets `live_stream_failed_at`, and does not fail the Run.

One Run's Stream is capped at 8 MiB of encoded event payloads or 10,000 entries, whichever is reached first. The adapter atomically rejects an append that would cross either bound; it never trims earlier entries because that would invalidate retained cursors. Reaching a bound follows the normal Live Stream failure path while Run execution and permanent Postgres history continue.

The worker awaits each Stream append sequentially in SDK event order with the existing 250 ms Redis operation timeout; there is no asynchronous publication queue. The first timeout or append failure sets `live_stream_failed_at`, disables every later Stream write for that Run, and lets model execution continue. This preserves strict event order and bounded memory while adding at most one bounded Redis delay to a degraded Run.

Every Stream key has a sliding 30-minute safety TTL from creation. Each successful append and the worker's existing 15-second heartbeat refresh it while live delivery remains healthy; heartbeat refresh changes only expiry metadata and never creates a replay entry. Terminal or error finalization stops refreshes and leaves the same 30-minute expiry in force. A refresh timeout or failure marks the Live Stream failed without failing the Run, so a crashed producer or failed finalization can never leave an immortal Redis key.

The resumable store's final status describes transport completion, not the Run Outcome. After successfully appending any terminal event—`RUN_FINISHED`, `RUN_ERROR`, or custom `RUN_INTERRUPTED`—the worker calls `finalize("done")`, because the complete event stream was delivered. If Live Stream publication fails before a terminal event, the worker sets `live_stream_failed_at` and best-effort calls `finalize("error", "Live stream unavailable")`; that error finalization starts the 30-minute cleanup TTL immediately even while model execution continues. The AG-UI Run Outcome still comes only from Postgres history.

Assistant text-delta rows are not written to or retained in Postgres. A healthy Redis Stream is kept alive and never trimmed while its Run is active; publishing its terminal event starts a 30-minute TTL. A failed Stream instead starts that TTL as soon as it is declared unavailable. Once either Stream expires, unfinished text is intentionally unrecoverable and complete Conversation history comes from Postgres. This supersedes the earlier decision to retain coalesced Assistant-delta Run events for the Conversation's lifetime and supersedes ADR-0008's cursorless Pub/Sub and two-source reconciliation design.

Redis availability does not determine the Run Outcome. If Redis publication or reading fails during a Run, the worker continues execution and still commits complete Assistant messages, Tool activity, and the terminal state to Postgres; MyMemo does not reintroduce a Postgres-to-SSE fallback or fail the Run merely to preserve its temporary stream. Live delivery may therefore end incomplete, and the client recovers the completed result from Conversation history after terminalization. A transport failure is not fabricated as `RUN_ERROR`, because that event describes the Run rather than its delivery channel.

Postgres remains the sole Run-admission boundary: chat-api atomically inserts the `queued` Run and its `run_started` event without contacting Redis. The worker claims that Run through the existing queue protocol, then acquires the per-Run Redis Stream and appends `RUN_STARTED` before invoking the model. If Stream acquisition or the initial append fails, the worker sets `live_stream_failed_at` and continues execution; completed messages, Tool activity, and the Outcome remain recoverable from Postgres. Token-level streaming is a required product capability but not a prerequisite for admitting or completing an individual Run. No `admitting` status or cross-system admission transaction is introduced.

On the first Redis publication failure, the worker disables further Live Stream publication for that Run and durably sets `live_stream_failed_at` on the Run without changing its execution status. This marker contains no message content and is not a Run event. The chat-api stream endpoint observes it and terminates the incomplete SSE transport rather than waiting indefinitely or exposing a potentially broken event suffix; `mymemo-web` then enters a recovering state and polls Conversation history until the Run terminalizes, replacing any provisional UI with the permanent Run projection.

The marker write is idempotent and monotonic. While the Run is active, `markLiveStreamFailedTx` requires the current worker's valid ownership lease; after the terminal transaction has cleared that lease, it permits only `live_stream_failed_at: null → now()` because the Run is immutable and cannot acquire another producer. Stale-run recovery sets the marker inside its own terminal transaction. A future feature that requeues a Run must introduce a Stream-writer fencing token before permitting another producer.

An SSE consumption attempt is complete only after the client observes the matching terminal event for the Run. EOF, connection loss, or parser termination before `RUN_FINISHED`, `RUN_ERROR`, or custom `RUN_INTERRUPTED` is a transport failure even when the HTTP body ends cleanly. When the Live Stream is still usable, the MyMemo client enters Reconnecting and resumes after its last cursor; when the Stream is marked failed or no longer retained, it enters Recovering and polls permanent history. `live_stream_failed_at` is not projected as a custom AG-UI event, and premature EOF is never interpreted as a successful Run. In particular, `history.resume()` must not return normally while its Assistant update remains `running`, because the upstream runtime treats an exhausted resume generator without terminal status as complete; it reconnects, recovers to an explicit terminal projection, or throws instead.

Reconnecting retries temporary `503` responses and network failures with full-jitter exponential backoff whose successive ceilings are approximately one, two, four, and then five seconds; five seconds remains the cap and there is no client-side retry deadline while the Run is active. A successful attempt resumes strictly after the in-memory cursor, while `410` immediately leaves Reconnecting and enters Recovering.

During Recovering, `mymemo-web` keeps the last provisional Assistant and Tool state visible, labels the Run as recovering, and continues to disable new sends while that Run is active. When terminal history becomes available, it replaces the entire provisional Run with the permanent projection; incomplete Assistant text may therefore disappear after an errored or interrupted Run.

Recovery fetches Conversation history immediately and then every two seconds with `limit=1`; the response contract still includes the active Run in addition to that newest-completed-Run limit. Polling stops when the target `runId` appears terminal, the user navigates away, or the request is aborted, and has no client-side completion deadline. Durable Run interruption remains available throughout Recovering.

MyMemo does not advertise resumability until real-Redis-plus-Postgres integration tests verify replay from zero and strictly after a cursor; `unstable_resume` always has a bound `history.resume()` and never falls back to a fresh Run; premature resume-generator exhaustion cannot fabricate completion; disconnects during text and Tool activity; Redis failure before Stream creation, mid-message, and after the terminal Postgres commit; queued interruption and stale-worker recovery without a producer; TTL expiry and both Stream caps; invalid cursors; ownership-isolated `404` responses; and full-refresh races with terminalization. Unit tests remain useful for encoding and Lua scripts but cannot substitute for these cross-system ordering checks.

Live Stream observability is separate from Run-outcome observability. The worker measures Stream acquisition role and failure, append/finalize/TTL-refresh failures, bound rejections, and Redis operation latency; chat-api measures reconnect `503` responses, recovery `410` responses, and the wait for initial Stream availability; `mymemo-web` measures transitions into Reconnecting and Recovering and the time until permanent-history recovery. Elevated Live Stream failure and recovery rates alert operators without being counted as Run failures. These signals may correlate on `runId`, but logs and metric labels must never contain serialized AG-UI events, Assistant text, Tool arguments or results, Redis credentials, or full Redis keys.
